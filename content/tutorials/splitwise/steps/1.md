The split type is the obvious **Strategy**: one interface, three implementations, chosen per expense.

```java
interface Split {
    /** participant → share, in participant order; shares must sum to amount */
    Map<String, Long> shares(long amount, List<String> participants);
}
```

```python
class Split(ABC):
    @abstractmethod
    def shares(self, amount: int, participants: List[str]) -> Dict[str, int]:
        """participant -> share, in participant order; shares must sum to amount"""
```

## EqualSplit

`amount / n` each, and the first `amount % n` participants get one extra unit. 100 split 3 ways is 34, 33, 33. In Python, `divmod(amount, n)` gives both at once, and a `dict` keeps insertion order, so building it in participant order is enough.

## ExactSplit(amounts)

The map's keys must be **exactly** the participants, and the values must sum to `amount`. Each value must be ≥ 0.

## PercentSplit(percents)

The keys must be exactly the participants, and the percents must sum to **100**. Each share is `floor(amount × p / 100)`. The leftover `amount − Σshares` is handed out **one unit at a time in participant order**.

Example: 100 at 33/33/34 → 33, 33, 34 (no leftover). 10 at 33/33/34 → floors 3, 3, 3 = 9, leftover 1 → 4, 3, 3.

Any violation is an error (Java `IllegalArgumentException`, Go `ErrInvalidSplit`, Python `ValueError`). That includes an empty participant list and `amount <= 0`.

> **Say in the interview:** *"Shares always sum to the amount exactly, because I distribute remainders deterministically. Money is never created or lost."*
