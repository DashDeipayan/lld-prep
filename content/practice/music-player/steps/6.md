Two parts.

**Extensibility.** The product team wants: a lock-screen widget and a scrobbler that records listens; a device picker that switches between phone speaker, Bluetooth headphones and a Chromecast TV mid-song, where each comes with its own vendor SDK; and headset buttons plus keyboard shortcuts that control playback. Name a pattern for each and sketch the interface.

**Concurrency.** The audio engine calls `player.trackEnded()` from its own thread when a song finishes. At almost the same instant the user taps **Next**. Describe what can go wrong and how you'd prevent it. Then: the Bluetooth headphones disconnect while a song is playing. What should happen, and on which thread does that event arrive?

## Extensibility

| Need | Pattern | Seam |
|---|---|---|
| Lock screen, scrobbler, lyrics panel | **Observer** | `PlayerListener { onSongChanged(song); onStateChanged(state); }` |
| Speaker / Bluetooth / Chromecast | **Adapter**, plus a `DeviceManager` registry for picking the active one | `AudioOutput { start(song); prepare(song, atSec); pause(); resume(); stop(); positionSec(); }` |
| Keyboard, headset, voice, remote | **Command** | `interface Command { void execute(Player p); }` with `PlayPause`, `Next`, `Previous`, `Seek(sec)`… |

### The device adapter

The vendor SDKs don't match each other or the player. A Cast session wants a media URL and milliseconds and has `setPaused(bool)`; Bluetooth wants an open stream and raw PCM frames. One adapter per device type converts:

```java
class CastOutput implements AudioOutput {          // Adapter: AudioOutput → CastSession
    private final CastSession session;              // vendor SDK, can't change it
    public void start(Song s)              { session.loadMedia(url(s), 0, true); }
    public void prepare(Song s, int atSec) { session.loadMedia(url(s), atSec * 1000L, false); }
    public void pause()                    { session.setPaused(true); }
    public void resume()                   { session.setPaused(false); }
    public void stop()                     { session.stopMedia(); }
    public int positionSec()               { return (int) (session.currentTimeMs() / 1000); }
}
```

Switching devices is then just: read `positionSec()` from the old output, `stop()` it, and `prepare(song, pos)` on the new one, plus `resume()` if the player was playing. The current **state** decides that last part (see step 4). Adding AirPlay next year means one new adapter; the player, states and queue don't change.

Commands decouple **input devices** from the player. A key-binding map `Key → Command` is configuration, and remote control just ships a serialised command over the network. Commands also give you a log of user actions for free.

The scrobbler is a listener with a rule ("count a listen after 30s or half the song"). It never touches player internals.

## The race

Without coordination:

1. The audio thread sees the end of song B and calls `trackEnded()` → `queue.next()` → cursor moves to C.
2. The UI thread processes **Next** → `queue.next()` → cursor moves to D.

The user skipped one song but **two** advanced. Worse, both threads call `out.start(...)` at once, and unsynchronised writes to `pos` can corrupt the cursor.

## Fixes

1. **Serialise every mutation.** Use one lock on the player (`synchronized` / `Mutex`), or better, a **single event-loop thread** that both the UI and the audio engine post messages to. The event loop is how real players are built: no locks in the logic, just a queue of events.
2. **Ignore stale events with a session token.** Every `start(song)` increments `playSession`, and the audio engine passes the session back in `trackEnded(session)`. If `session != playSession`, the user already moved on, so drop the event. Serialisation alone doesn't fix this: the stale "ended" event would still be processed after the Next.
3. **Device events go through the same door.** "Headphones disconnected" arrives on an OS callback thread, so it is serialised like everything else. The player pauses (if playing) and moves to the speaker. That ordering matters: pause first, *then* switch, so the speaker never plays a second of audio. The session token also covers this: a late "track ended" from the old Bluetooth output carries an old session and is dropped.
4. **Notify listeners outside the lock** (or post them to the UI thread) so a slow scrobbler can't block playback.

> **Say:** *"The queue is pure and single-threaded. All inputs, from buttons or the audio engine, become events on one loop, and stale audio events are dropped by a session token."*
