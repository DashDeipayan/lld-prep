The interviewer has 5 minutes left and asks four follow-ups. Write a 2–4 line answer for each, naming **which classes change**:

1. *"Add EV charging spots. EVs should prefer them; others can use them only if nothing else is free."*
2. *"Users can reserve a spot for a time window."*
3. *"We now run 200 lots. How does this change?"*
4. *"Add payment at exit: card, UPI, cash. Payments can fail."*

<!-- answer -->

## 1. EV charging spots

- `Spot` gets a `boolean hasCharger`; `Vehicle` gets `boolean electric`. That's data, not new subclasses.
- New `EvAwareSelector implements SpotSelector`. For an EV, pick the first free charger spot, otherwise fall back. For a non-EV, pick the first free non-charger spot, otherwise any.
- `ParkingLot` doesn't change. That's the payoff of making selection a strategy in step 5.

## 2. Reservations

- New `Reservation(id, plate, spotId, from, to)` and a `ReservationService` holding reservations per spot (sorted by start time, so overlap checks are O(log n)).
- The free-spot filter becomes "free **and** not reserved for [now, now + grace]". The cleanest place for that is a `SpotAvailability` predicate the lot asks, rather than piling rules into `Spot`.
- On arrival, `park(vehicle, reservationId)` uses the reserved spot directly. Mention no-show expiry (release after N minutes) and that overlapping holds need the same lock (or a DB unique constraint).

## 3. 200 lots

- The in-memory design is **one lot per process or partition**. Add a `LotRegistry` / `lotId` on every API, and route requests to the owning instance by `lotId`.
- State moves to a database: a `spots` table with a row-level lock or `UPDATE ... WHERE vehicle IS NULL` (an atomic conditional update replaces the mutex), and a `tickets` table.
- Cross-lot features (find the nearest lot with space) read from a cache that each lot's display events update. Listeners become a message bus.

## 4. Payments

- `unpark` splits in two: `checkout(ticketId) → Invoice` (computes the fee, ticket goes `PAYMENT_PENDING`) and `pay(invoiceId, PaymentMethod)`. The spot is freed only after a successful payment or a manual override.
- `PaymentMethod` is a **Strategy** (or one `PaymentGateway` interface with card/UPI/cash adapters).
- The ticket is now a **state machine**: `ACTIVE → PAYMENT_PENDING → PAID → EXITED`, with `PAYMENT_FAILED → PAYMENT_PENDING` for retries. Use **idempotency keys** so a retried payment never charges twice.

> **How to close:** *"The two strategies and the observer took every one of these changes without editing `ParkingLot`, apart from the payment flow, which genuinely changes the lifecycle."*
