## Entities

| Entity | Kind | Holds | Owns behaviour |
|---|---|---|---|
| `VehicleType` | enum | `BIKE`, `CAR`, `TRUCK`, each with a `minSize` | none (it's data) |
| `SpotSize` | enum (ordered) | `SMALL < MEDIUM < LARGE` | comparison |
| `Vehicle` | value object | plate, type | none |
| `Spot` | class | id (`F1-M3`), floor, size, current vehicle | `canFit(v)`, `occupy(v)`, `vacate()` |
| `Ticket` | value object | ticketId, plate, type, spotId, entryTime | none |
| `Receipt` | value object | ticket, exitTime, fee | none |
| `PricingStrategy` | interface | none | `fee(type, duration)` |
| `SpotSelector` | interface | none | `select(freeSpots, vehicle)` |
| `ParkingListener` | interface | none | `onEvent(event)` |
| `ParkingLot` | class (facade) | spots, active tickets, plates inside, strategies, listeners | `park`, `unpark`, `available(size)` |
| `Clock` | interface | none | `now()` (injected so tests control time) |

## The choice you're *not* making

**No `Car extends Vehicle` / `Truck extends Vehicle` hierarchy.** The vehicle types differ only in *data* (which spot sizes they fit), not in behaviour. An enum with a `minSize` turns the fitting rule into one comparison, `spot.size >= vehicle.type.minSize`, and adding a `VAN` is one line.

Use polymorphism where **behaviour varies**: pricing, selection and listeners.

> **Floor as a class?** It's optional. A `Floor` class is fine if floors get behaviour later (per-floor display, closing a floor for maintenance). A floor *number* on each spot is enough for the requirements. Say which you picked and why.
