Answer each follow-up in 2–4 lines, naming **what changes**:

1. *"Analysts want to try a new rule on live traffic without affecting decisions."*
2. *"The data science team has an ML model that returns a fraud probability. Plug it in."*
3. *"Large merchants want their own thresholds."*
4. *"We're running 50 instances of this service. What breaks?"*

<!-- answer -->

## 1. Shadow mode

- Add a `mode` to each rule config: `ACTIVE | SHADOW`. The factory wraps shadow rules in a `ShadowRule` **decorator** that evaluates, records the would-be result to a separate log or metric, and returns `pass` to the engine.
- Analysts compare shadow hits against actual fraud outcomes, then flip the rule to `ACTIVE` with a config change. No code changes, and the engine is untouched.

## 2. ML model

- It's **just another `Rule`**: `ModelScoreRule(client, weight)` calls the model service and maps probability to score (`p × 100 × weight`). If it's above a cut-off, it can return a hard REVIEW.
- Wrap it in the `TimedRule` decorator (the model is the slowest dependency). On timeout, score 0 plus a metric, or REVIEW, depending on policy. Put it **last** so cheap rules can short-circuit first.

## 3. Per-merchant thresholds

- `DecisionPolicy` is already a strategy. Add a `PolicyResolver` that takes `merchantId` and returns a `ThresholdPolicy`, with a default. The resolver lives in the `RuleSet` snapshot, so it hot-reloads with everything else.
- Some merchants may also want different *rules*. The `RuleSet` can be keyed by merchant segment.

## 4. 50 instances

- **Velocity state** is the thing that breaks. In-memory counters only see 1/50th of the traffic. Move `VelocityStore` behind its interface to **Redis** (atomic Lua), or consistently route each user to one instance. The rules don't change.
- **Config**: store it in a DB or config service, and have instances poll or subscribe and swap snapshots. The version stamp on assessments shows which config each instance used.
- **Lists** (blocklists): a cached `ListStore` with short TTLs or pub/sub invalidation.
- **Audit**: listeners publish to a durable queue (Kafka) rather than writing synchronously, so the 50 ms budget holds.

> **Close with:** *"Because state sits behind store interfaces and config is a versioned snapshot, scaling out mostly means swapping implementations, not redesigning."*
