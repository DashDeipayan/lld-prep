Three questions.

1. **Race.** The velocity limit is 5 per 10 minutes, and the user already has 4. Two payments arrive on different threads at the same moment. What can go wrong in a naive implementation, and how do you fix it?
2. **Hot reload.** An analyst changes the thresholds while 1,000 assessments are running. What should those in-flight assessments see, and how do you implement it?
3. **Extensibility.** Analysts want *"new device AND amount > 50k"*, per-rule timeouts and metrics, and to trial a new rule without affecting decisions. What patterns?

## 1. The check-then-act race

A naive rule does `count = store.count(user)`, then `if count >= 5 → flag`, then `store.add(now)`. Both threads read **4**, both pass, both add, and the user ends at 6. This is the same race as a double-booked seat.

**Fix: make record-and-count one atomic operation.**

- In memory: a per-key lock (`ConcurrentHashMap.compute`, a striped lock, or one mutex for a small service) around *append, evict, count*.
- Distributed: one **Redis Lua script** doing `ZADD`, `ZREMRANGEBYSCORE` and `ZCARD` atomically, or route all of a user's traffic to one partition.

With atomic record-and-count, one thread sees 5 and the other sees **6 > 5**, so it's flagged.

## 2. Hot reload: immutable snapshots

- Config is an **immutable `RuleSet`** (rules + policy + version) held in an `AtomicReference` / `atomic.Pointer`.
- `assess` reads the reference **once** at the start, so it uses one consistent config end to end.
- `reload` builds a new `RuleSet` (validating it first), then swaps the reference. There are no locks on the read path, and nobody sees half-updated thresholds.
- Store the version in each `Assessment` for reproducibility. Keep the previous version for **instant rollback**.

## 3. Patterns

| Need | Pattern |
|---|---|
| `AND` / `OR` / `NOT` of rules from config | **Composite / Specification**: `AllOf(rules)`, `AnyOf(rules)`, `Not(rule)` are themselves `Rule`s |
| Build rules from JSON | **Factory / registry**: `type → constructor` map, so a new rule type registers itself |
| Per-rule timeout, metrics, error handling | **Decorator**: `TimedRule(inner, 20ms)`, `MeteredRule(inner)` wrap any rule |
| Trial a new rule | **Shadow mode** decorator: evaluates and logs, but returns `pass` to the engine |
| Audit, review cases, alerts | **Observer**: `DecisionListener`s |

> **Say:** *"Every rule is a strategy. Combining is a composite. Cross-cutting concerns are decorators. Config is an immutable snapshot swapped atomically. Velocity uses atomic record-and-count."*
