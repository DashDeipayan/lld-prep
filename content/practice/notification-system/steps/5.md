For each requirement, name the **pattern** and sketch the **interface**:

1. Adding WhatsApp, or switching SMS from Twilio to another provider.
2. Opt-outs, muted categories, quiet hours and per-user rate limits.
3. Retries, provider failover and metrics around sending.
4. Callers and dashboards need to know when status changes.
5. Requests have many optional fields.

## 1. Channels and providers → **Strategy + Adapter**, held in a **registry**

```java
interface ChannelSender { void send(Message m) throws SendException; }

class TwilioSmsSender implements ChannelSender {     // Adapter: Twilio's API → our interface
    public void send(Message m) throws SendException { /* twilio.messages.create(...) */ }
}

Map<Channel, ChannelSender> senders = Map.of(Channel.SMS, new TwilioSmsSender(...), ...);
```

```go
type Sender interface{ Send(m Message) error }

senders := map[Channel]Sender{SMS: twilioSMS, Email: sesEmail}
```

```python
class ChannelSender(ABC):
    @abstractmethod
    def send(self, message: Message) -> None: ...

senders = {Channel.SMS: TwilioSmsSender(...), Channel.EMAIL: SesEmailSender(...)}
```

Adding WhatsApp means adding `Channel.WHATSAPP` and a `WhatsAppSender`, then registering it. Switching providers means swapping the adapter. The dispatcher doesn't change.

## 2. Checks → **Chain of Responsibility**

```java
interface DeliveryFilter {
    Optional<String> reject(Notification n, Channel c, UserPreferences p);   // reason, or empty to pass
}
// PreferenceFilter, CategoryMuteFilter, QuietHoursFilter, RateLimitFilter: run in order, the first rejection wins
```

The order matters. Run cheap checks first, and run the rate limiter **last**, so skipped messages don't use up a user's quota.

## 3. Cross-cutting sending behaviour → **Decorator**

`RetryingSender(inner, policy)`, `FailoverSender(primary, secondary)`, `MeteredSender(inner)`. They stack: `Metered(Failover(Retrying(twilio), Retrying(other)))`.

## 4. Status changes → **Observer**

`DeliveryListener.onStatus(delivery)`: `StatusStore`, `MetricsListener`, `WebhookListener`. Provider receipts (delivered, bounced) arrive through the same path.

## 5. Optional fields → **Builder**

```java
Notification n = Notification.builder("order-42-shipped", userId, "order_shipped")
    .category("orders").priority(Priority.HIGH)
    .param("orderId", "42").channels(EMAIL, PUSH)
    .build();
```

Go uses a struct literal or functional options, and Python uses keyword arguments with defaults, so the Builder is mostly a Java thing.
